# Tauri OpenHarmony 多窗口特性实现文档

## 第一部分：架构设计

### 1.1 总体架构

Tauri 在 OpenHarmony 上的多窗口支持采用 **四层栈** 架构，每一层负责不同职责，通过 `windowId` 进行跨层路由：

```
┌─────────────────────────────────────────────────────────┐
│  Layer 4: Tauri App (用户代码)                          │
│  WebviewWindowBuilder::new(app, label, url)              │
│  .inner_size(800,600).data_directory(dir).build()       │
├─────────────────────────────────────────────────────────┤
│  Layer 3: tauri-runtime-wry (胶水层)                    │
│  1. WindowBuilder.with_label(label) → tao               │
│  2. create_window() → tao WindowBuilder.with_label()    │
│  3. window.window_id() → wry WebViewBuilder             │
│     .with_window_id(window_id)                          │
├─────────────────────────────────────────────────────────┤
│  Layer 2: tao + wry (平台抽象层)                        │
│  tao: Window::new() 判断主/子窗口                       │
│    OHOSWindowKind::UIAbility → windowId=0, 复用主窗口    │
│    OHOSWindowKind::Float → create_os_window(), 新建OS窗口│
│    None → 首窗口默认UIAbility, 后续默认Float(AtomicBool) │
│  wry: InnerWebView::new() 读取 window_id                │
│    传递给 openharmony-ability WebViewBuilder            │
├─────────────────────────────────────────────────────────┤
│  Layer 1: openharmony-ability (Rust + ArkTS)            │
│  Rust: AtomicI64 全局 ID 分配                           │
│    → napi 调用 ArkTS createOSWindow                    │
│  ArkTS: WindowManager 单例管理                          │
│    → window.createWindow() (OHOS API)                  │
│    → loadContentByName("FloatWindow", LocalStorage)     │
│    → ProxyJsHelper 解决异步竞态                         │
└─────────────────────────────────────────────────────────┘
```

### 1.2 核心设计原则

| 原则 | 说明 |
|------|------|
| **windowId 全局路由** | 所有窗口操作（创建 WebView、加载 URL、获取安全区）均通过 `windowId` 路由到正确的窗口实例，不再依赖隐式的单窗口假设 |
| **主窗口固定 ID=0** | 主窗口（OHOSWindowKind::UIAbility）windowId 固定为 `0`，所有子窗口 ID 从 `1` 开始递增 |
| **主窗口不创建 OS 窗口** | 主窗口复用 `NativeAbility` 已有的 `DefaultXComponent` 容器，只有子窗口调用 `create_os_window` 创建新的 OS 级窗口 |
| **异步竞态代理模式** | Rust 调用 `createOSWindow` 是异步的，但 Rust 立即获得返回值。ArkTS 侧通过 `ProxyJsHelper` 缓存操作，待控制器就绪后回放 |
| **LocalStorage 窗口隔离** | 子窗口通过 `LocalStorage`（而非 AppStorage）接收 `windowId`，确保每个窗口的数据隔离 |
| **ArkHelper 组件外置** | ArkHelper 不再绑定到 `DefaultXComponent` 的 `this` 指针，改为独立工厂函数 `createArkHelper()`，通过 WindowManager 按 windowId 路由 |

### 1.3 窗口创建流程（端到端）

```
Rust: WebviewWindowBuilder::new(app, "window_a_1", url)
  → tauri-runtime-wry: window_builder.with_label("window_a_1")
  → tao: Window::new(pl_attrs.label="window_a_1", pl_attrs.window_kind=None)
    → UIABILITY_CREATED=true (主窗口已存在) → is_main=false → 调用 create_os_window("window_a_1", TypeFloat)
    → openharmony-ability Rust: NEXT_WINDOW_ID.fetch_add(1) → id=1
    → napi 调用 ArkTS: createOSWindow({name, type, windowId:1, width, height, x, y})
    → ArkHelper.createOSWindow(config)
      → WindowManager.createSubWindow(name, type, 1, width, height, x, y)
        → window.createWindow(config)                  [OHOS API]
        → LocalStorage.setOrCreate('windowId', 1)
        → win.loadContentByName("FloatWindow", storage)
        → FloatPage.aboutToAppear() 接收 windowId=1
        → FloatPage 渲染 DefaultXComponent({windowId: 1})
        → DefaultXComponent.aboutToAppear():
           → wm.registerUIContext(1, uiCtx)
           → wm.registerController(1, controller)
           → registerController 触发: 回放 pendingInit + 绑定 ProxyJsHelper

  → tao 返回 window_id=Some(1) → tauri-runtime-wry 获取 window.window_id()=1
  → wry: webview_builder.with_window_id(1)
    → openharmony-ability WebViewBuilder.window_id(1)
    → napi 调用 ArkTS: createWebview({url, id, windowId:1})
    → ArkHelper.createWebview(data)
      → wm.getController(1) 查找控制器
      → 若已就绪: 直接 addWebview(init)
      → 若未就绪: 创建 ProxyJsHelper, 缓存操作, 返回代理给 Rust
      → 当 registerController(1) 触发后: proxy.bindToRealController() 回放所有缓存操作
```

### 1.4 两路径 WebView 创建

| 路径 | 条件 | 说明 |
|------|------|------|
| **Path 1** | windowId=0 (主窗口) | WebView 在已有 `DefaultXComponent` 内创建，走 `render(helper, rootSlot)` 模式 |
| **Path 2** | windowId>0 (子窗口) | WebView 在新 `DefaultXComponent` 内创建，走 `registerController + addWebview` 模式 |

## 第二部分：实现细节

### 2.1 关键组件详解

#### WindowManager.ets — 多窗口中枢

```typescript
class WindowManager {
  // 数据存储
  windows: Map<number, arkWindow.Window>           // OS 窗口实例
  controllers: Map<number, RustWebviewNodeController> // WebView 控制器
  uiContexts: Map<number, UIContext>                // UI 上下文
  pendingInits: Map<number, WebViewInitData>        // 等待回放的初始化数据
  pendingUrls: Map<number, string>                  // 等待加载的 URL
  pendingJsHelperProxies: Map<number, ProxyJsHelper> // 等待绑定的代理

  // 核心方法
  createSubWindow(name, type, windowId, w, h, x, y) // 创建子窗口
  registerController(id, controller)                // 注册控制器 → 触发回放
  registerUIContext(windowId, ctx)                  // 注册 UIContext
  loadUrl(id, url)                                 // 加载 URL（队列或直接）
  getController(id) / getWindow(id) / getUIContext(id) // 按 ID 查找
}
```

**核心流程**: `registerController` 是关键触发点 — 当控制器注册后，会依次：
1. 回放 `pendingInits` 中的 WebView 初始化数据
2. 加载 `pendingUrls` 中缓存的 URL
3. 绑定 `pendingJsHelperProxies` 中的代理到真实控制器

#### ArkHelper.ets — 窗口无关的工厂函数

```typescript
function createArkHelper(): ArkHelper {
  return {
    createWebview(data): JsHelper {
      const wm = WindowManager.getInstance();
      const controller = wm.getController(data.windowId);
      if (controller) {
        // Path A: 控制器已就绪，直接创建 WebView
        controller.addWebview(data);
        return controller;
      } else {
        // Path B: 控制器未就绪，返回 ProxyJsHelper
        const proxy = new ProxyJsHelper();
        wm.queueWebviewInit(data.windowId, data);
        wm.registerPendingJsHelperProxy(data.windowId, proxy);
        return proxy;
      }
    },
    createOSWindow(config): void {
      wm.createSubWindow(config.name, config.type, config.windowId, ...);
    },
    loadUrl(id, url): void { wm.loadUrl(id, url); },
    // ...
  };
}
```

**设计要点**: 不使用 `this` 持针，所有操作通过 `WindowManager.getInstance()` 按 windowId 路由，确保组件实例无关性。

#### ProxyJsHelper — 异步竞态解决方案

```typescript
class ProxyJsHelper implements JsHelper {
  private realController: JsHelper | null = null;
  private pendingOperations: Array<() => void> = [];

  bindToRealController(real: JsHelper): void {
    this.realController = real;
    // 回放所有缓存操作
    for (const op of this.pendingOperations) { op(); }
    this.pendingOperations = [];
  }

  loadUrl(url: string): void {
    if (this.realController) {
      this.realController.loadUrl(url);
    } else {
      this.pendingOperations.push(() => this.realController!.loadUrl(url));
    }
  }
  // 其他方法同理: zoom, refresh, runJavaScript, ...
}
```

**竞态根因**: Rust 调用 `createOSWindow`（async ArkTS）→ 立即获得 Promise → 调用 `createWebview` → 此时 `FloatPage.aboutToAppear()` 尚未完成，控制器不存在。`ProxyJsHelper` 返回给 Rust 一个可用引用，所有操作被缓存，待控制器注册后通过 `bindToRealController()` 回放。

#### DefaultXComponent.ets — 双模式组件

```typescript
@Component
struct DefaultXComponent {
  @Prop windowId: number = 0;
  @Prop moduleName: string = "";

  aboutToAppear(): void {
    // 注册 UIContext 到 WindowManager
    wm.registerUIContext(this.windowId, this.getUIContext());

    if (this.isMainWindow()) {
      // 主窗口路径: 加载原生模块, render(helper, rootSlot)
      const helper = createArkHelper();
      const result = render(helper, this.rootSlot);
      wm.registerController(0, result.controller);
    } else {
      // 子窗口路径: 仅注册控制器
      const controller = new RustWebviewNodeController(...);
      wm.registerController(this.windowId, controller);
    }
  }
}
```

#### tao — 窗口创建决策

```rust
// src/platform_impl/ohos/mod.rs
static UIABILITY_CREATED: AtomicBool = AtomicBool::new(false);

impl Window {
  pub(crate) fn new(el, attrs, pl_attrs) -> Result<Self> {
    let is_main_window = match pl_attrs.window_kind {
      Some(OHOSWindowKind::UIAbility) => true,
      Some(OHOSWindowKind::Float) => false,
      None => !UIABILITY_CREATED.load(Ordering::SeqCst), // 首窗口默认 UIAbility
    };

    if is_main_window {
      if UIABILITY_CREATED.swap(true, Ordering::SeqCst) {
        return Err(os_error!(OsError)); // UIAbility 单例约束
      }
    }

    let window_id = if is_main_window {
      Some(0)  // 主窗口: windowId=0, 不创建新OS窗口
    } else {
      let label = pl_attrs.label.unwrap_or(attrs.title);
      create_os_window(label, OHOSWindowType::TypeFloat as i32).ok()
    };

    Ok(Self { app, window_id })
  }

  pub fn window_id(&self) -> Option<i64> { self.window_id }
}
```

**关键决策**: 使用 `OHOSWindowKind` 枚举而非 label 字符串判断主/子窗口。`None` 时通过 `UIABILITY_CREATED` AtomicBool 自动推断：第一个窗口默认为 UIAbility，后续窗口默认为 Float。

### 2.2 竞态条件详解

**问题**: Rust 和 ArkTS 运行在同一线程的 Event Loop 上。Rust 调用 `createOSWindow`（async ArkTS）→ 获得 Promise → 继续调用 `createWebview` → 但此时 `FloatPage.aboutToAppear()` 尚未执行，控制器不存在。

**解决方案**: 三级队列 + 代理回放

```
Rust 调用 createOSWindow → ArkTS async 开始创建窗口
Rust 调用 createWebview → ArkHelper.createWebview(windowId=1)
  → wm.getController(1) = null (控制器未就绪)
  → 创建 ProxyJsHelper, 缓存所有操作
  → wm.queueWebviewInit(1, initData)
  → wm.registerPendingJsHelperProxy(1, proxy)
  → 返回 proxy 给 Rust

... FloatPage.aboutToAppear() 执行 ...
  → wm.registerController(1, controller)
    → 回放 pendingInits[1]: controller.addWebview(initData)
    → 加载 pendingUrls[1]: controller.loadUrl(url)
    → 绑定 pendingJsHelperProxies[1]: proxy.bindToRealController(controller)
      → 回放所有缓存的 JsHelper 操作
```

## 待办事项 (TODO)

### TODO-1: Rust 调用 ArkTS 的错误处理机制待完善

当前 Rust → napi → ArkTS 的错误传播链在多处被截断。例如 `createWebview` 失败时曾返回空 stub `{} as JsHelper`，导致 Rust 侧无法感知真实错误（已修复为返回 `ProxyJsHelper` 兜底，但仍不是完善的错误传播方案）。后续应统一错误传播策略，所有 napi 跨层调用失败时均应通过 `Error::from_reason()` 将 ArkTS 侧错误信息传回 Rust。

### TODO-2: 窗口尺寸参数化

当前 `create_os_window` 中窗口尺寸和位置硬编码为 `width=800, height=600, x=100, y=100`，无法从 tauri 侧的 `WebviewWindowBuilder.inner_size()` 等参数传递下来。后续应让 `create_os_window` 从 tao 的 WindowAttributes 中获取窗口尺寸信息，并通过 config 对象传递给 ArkTS。

### TODO-3: 子窗口销毁时的清理逻辑

当前没有子窗口销毁时从 WindowManager 中移除 `controllers/uiContexts/windows/pendingInits/pendingUrls/pendingJsHelperProxies` 的逻辑。FloatPage 的 `destroyWindow()` 会销毁 OS 窗口，但 WindowManager 中的注册数据不会自动清理，长期运行可能造成内存泄漏。后续应在 WindowManager 中增加 `unregisterController(id)`、`unregisterWindow(id)`、`unregisterUIContext(id)` 方法，并在窗口销毁事件回调中调用。

### TODO-4: 子窗口权限声明

创建子窗口需要 `ohos.permission.SYSTEM_FLOAT_WINDOW` 权限。后续应在文档和配置中补充权限声明说明，包括 module.json5 中的 `requestPermissions` 配置以及运行时的权限申请流程。

### TODO-5: scriptRules 自定义协议支持

OHOS `javaScriptOnDocumentStart` API 的 `scriptRules` 对 http/https 以外的自定义协议（如 `tauri://`、`resource://`）存在限制：
- `["*"]` 仅匹配 http/https 协议，不匹配自定义协议
- 自定义协议不支持精确匹配和模糊匹配
- 自定义协议的规则必须以 `://` 结尾，例如 `"tauri://"`, `"resource://"`

当前 ArkHelper 中所有 ScriptItem 的 `scriptRules` 统一设为 `["*"]`，导致 IFRAME_STYLE 等初始化脚本在 `tauri://localhost/` 等自定义协议页面上无法注入。后续需要在脚本注入链路（tauri config → wry → openharmony-ability → ArkTS）中传播协议名称，将 `scriptRules` 从 `["*"]` 改为包含自定义协议规则的数组，如 `["*", "tauri://"]`。

## 第三部分：窗口类型可配置化设计（OHOSWindowKind）

### 3.1 问题背景

原有实现通过字符串 `label == "main"` 判断主窗口，硬编码 `TYPE_FLOAT` 为子窗口类型。这种做法有以下问题：

1. **主窗口识别依赖魔法字符串** — `pl_attrs.label.as_deref() == Some("main")` 是脆弱的
2. **窗口类型不可配置** — 子窗口类型始终为 TYPE_FLOAT，用户无法选择
3. **缺乏单例约束** — 无法阻止重复创建主窗口

### 3.2 OHOSWindowKind 枚举设计

引入 `OHOSWindowKind` 枚举替代 label-based 检测，当前仅支持两种类型：

```rust
pub enum OHOSWindowKind {
  UIAbility,  // 主窗口 — 复用 UIAbility 已有的窗口容器 (DefaultXComponent)
  Float,      // 子窗口 — 创建新的 OS 级浮动窗口 (TYPE_FLOAT=8)
}
```

**设计原则**：
- `UIAbility` 对应主窗口（window_id=0），复用 OHOS Ability 生命周期提供的窗口容器
- `Float` 对应子窗口（window_id>0），创建新的 OS 级浮动窗口
- 当前仅支持 Float，不支持 Dialog（后续可扩展）
- **默认行为基于 UIABILITY_CREATED 标志** — `window_kind` 为 None 时，首个窗口默认 UIAbility，后续窗口默认 Float
- **UIAbility 单例约束** — 只允许创建一个 UIAbility 窗口，违反则返回错误

### 3.3 UIAbility 单例约束

使用静态 `AtomicBool` 标志位实现单例约束：

```rust
static UIABILITY_CREATED: AtomicBool = AtomicBool::new(false);

// 在 Window::new() 中
if is_main_window {
    if UIABILITY_CREATED.swap(true, Ordering::SeqCst) {
        return Err(error::OsError::new(
            "OHOS UIAbility window already exists; only one is allowed",
            None,
        ));
    }
}
```

**行为**：
- 第一次创建 UIAbility 窗口 → 成功，标志位设为 true
- 第二次创建 UIAbility 窗口 → 失败，返回错误
- 创建 Float 窗口 → 不受限制，可创建多个
- 标志位不会重置（UIAbility 窗口绑定应用生命周期，不可重建）

### 3.4 调用链路变化

**旧链路（label-based）**：

```
Tauri WebviewWindowBuilder
  → with_label(&config.label)                    ← 仅传递 label
    → tao: PlatformSpecificWindowBuilderAttributes { label }
      → Window::new()
        → is_main_window = pl_attrs.label.as_deref() == Some("main")  ← 字符串比较
          → 硬编码 OHOSWindowType::TypeFloat
```

**新链路（enum-based）**：

```
Tauri WebviewWindowBuilder
  → .ohos_window_kind(OHOSWindowKind::Float)    ← 显式指定窗口类型
    → Tauri WindowBuilder.ohos_window_kind = Some(Float)
      → build_internal() → window_builder.ohos_window_kind(kind)
        → tauri-runtime-wry: WindowBuilderWrapper.ohos_window_kind(kind)
          → tao: WindowBuilderExtOpenHarmony::with_window_kind(kind)
            → PlatformSpecificWindowBuilderAttributes { label, window_kind }
              → Window::new()
                → is_main_window = match pl_attrs.window_kind {
                    Some(UIAbility) => true,
                    Some(Float) => false,
                    None => !UIABILITY_CREATED.load(SeqCst)  ← 首窗口默认 UIAbility
                  }
                  → UIAbility: window_id=0, 不创建 OS 窗口
                  → Float: window_type=8, 调用 create_os_window
```

### 3.5 各层修改详情

#### 3.5.1 tao 层（`tao/src/platform_impl/ohos/mod.rs`）

```rust
// 新增枚举
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub enum OHOSWindowKind {
  UIAbility,
  Float,
}

static UIABILITY_CREATED: AtomicBool = AtomicBool::new(false);

// 修改结构体
pub struct PlatformSpecificWindowBuilderAttributes {
    pub label: Option<String>,
    pub window_kind: Option<OHOSWindowKind>,  // 新增, None 时自动推断
}

// Window::new() 修改 — None 首窗口默认 UIAbility, 后续默认 Float
let is_main_window = match pl_attrs.window_kind {
  Some(OHOSWindowKind::UIAbility) => true,
  Some(OHOSWindowKind::Float) => false,
  None => !UIABILITY_CREATED.load(Ordering::SeqCst),
};

if is_main_window {
    if UIABILITY_CREATED.swap(true, Ordering::SeqCst) {
        return Err(os_error!(OsError)); // 单例约束
    }
}

let window_type = if is_main_window { 0 } else { OHOSWindowType::TypeFloat as i32 };
```

## 第四部分：多 UIAbility 实例可行性分析

> 参考代码：`demo3signature/entry/src/main/ets/pages/Index.ets` 的 `startNewAbility()` 函数。
> 本部分只做可行性分析，不含落地实施方案。

### 4.1 startNewAbility 机制

```typescript
async startNewAbility() {
  let context = getContext(this) as common.UIAbilityContext;
  let want: Want = {
    bundleName: context.applicationInfo.name,
    abilityName: 'EntryAbility'          // 复用同一 EntryAbility，不声明第二个 Ability
  };
  await context.startAbility(want);
}
```

`context.startAbility({abilityName:'EntryAbility'})` 让系统创建同 EntryAbility 类的**新实例**，触发完整 `onCreate → onWindowStageCreate(windowStage) → onForeground`。每个新实例由系统分配独立的 `WindowStage`、独立主窗口、独立生命周期。

关键点：

- **不新增第二个 UIAbility 声明**。`want.abilityName` 指向已有 EntryAbility，系统创建的是同类新实例，不是新的 Ability 类型。
- **不需要新 .ets 文件、不需要改模板变量、不需要新 srcEntry**。EntryAbility 类只声明一次，复用。
- 调用极简：一个 `context.startAbility(want)`，无返回值（异步），系统回调新实例生命周期。

### 4.2 前提：launchType 必须是 standard

`launchType` 决定 `startAbility` 的行为：

| launchType | startAbility({abilityName:'EntryAbility'}) 行为 |
|-----------|------------------------------------------------|
| `singleton`（省略默认） | 全局单实例，后续 startAbility 不新建窗口，走 `onNewWant` 回调 |
| `standard` | **每次创建新实例**，触发新 `onCreate` + 新 `onWindowStageCreate` + 新主窗口 |
| `specified` | `onAcceptWant` 决定匹配已有实例或新建 |

当前 Tauri 模板 `entry_*/src/main/module.json5` **未设 launchType**（默认 singleton）。在 singleton 下，`startAbility` 这条路径**不会新建窗口**，只会触发已有实例的 `onNewWant`。要多实例必须把 EntryAbility 的 `launchType` 改为 `standard`。

> 这是唯一与 `module.json5` 相关的改动点——改 EntryAbility 的 `launchType` 字段值，不是新增 Ability 声明。

### 4.3 多 UIAbility 实例的资源隔离

每个新 EntryAbility 实例由系统分配独立资源：

| 资源 | 隔离情况 |
|------|---------|
| `WindowStage` | 独立，系统在 `onWindowStageCreate` 分配 |
| 主窗口（`getMainWindowSync()`） | 独立，每个 WindowStage 一个 |
| 生命周期（onCreate/Foreground/Background/Destroy） | 独立 |
| 最近任务卡片 | 独立（每个实例一张卡片） |
| ArkUI 树 / 组件状态 | 独立，跨实例不共享 |
| Rust 进程内存（AppHandle、事件总线、插件状态） | **共享**（同 HAP 同进程） |
| ArkTS JS 引擎 / `WindowManager` 单例 | **共享**（同进程同引擎） |
| `NEXT_WINDOW_ID` 全局原子量 | **共享** |

同进程共享是多 UIAbility 实例能在 Tauri 单 Runtime 抽象下工作的前提：跨实例的状态同步不是跨进程 IPC 问题，Rust 侧 `AppHandle` 天然跨实例可见。

### 4.4 核心设计变更：windowId 语义与 UIAbility 判定解耦

当前适配以 `windowId === 0` 判断「是否 UIAbility 主窗口」（resize/move 守卫、`getWindow` 路由等大量 `wid === 0` 特判）。引入多 UIAbility 实例后，此判定**失效**：新实例的主窗口 windowId > 0（从 `NEXT_WINDOW_ID` 分配），但它同样是 UIAbility 主窗口、同样受系统管理。

**新语义**：

| 概念 | 定义 |
|------|------|
| `windowId = 0` | **仅**表示「第一个默认主窗口」，无其他含义。是首实例 EntryAbility 主窗口的固定 ID，向后兼容 |
| `windowId > 0` | 从 `NEXT_WINDOW_ID` 分配的 ID，可能是 Float 子窗口，也可能是新 UIAbility 实例的主窗口 |
| 是否 UIAbility | **不靠 windowId 判断**，通过新增枚举参数表示 |

即：windowId 只回答「是哪个窗口」，不回答「是不是 UIAbility 主窗口」。后者由独立的枚举参数（窗口性质）回答。

**对现有 `wid === 0` 特判的影响**：所有以 `wid === 0` 判断「UIAbility 主窗口、系统管理、resize/move no-op」的代码需改为查窗口性质枚举。windowId=0 的特判仅保留在「首实例主窗口固定 ID」这一向后兼容语义上（如 `getWindow(0)` 从主 `windowStage` 取主窗口），不再承载「是否 UIAbility」的判断职责。

### 4.5 能力边界（多 UIAbility 实例不解决的）

| 限制 | 根因 | 说明 |
|------|------|------|
| 主窗口 resize/move | UIAbility 主窗口系统管理 | 每个实例主窗口都返回 1300002，多实例不解决。要 resize/move 必须用 Float 子窗口 |
| 跨窗口 z-order | OHOS 无跨 Ability z-order API | 置顶不因多实例获得 |
| 跨窗口共享 WebView/组件 | 跨实例无共享 ArkUI 树 | 无法共享 |

### 4.6 与现有 Tauri 适配的关系

当前 `OHOSWindowKind` 有 `UIAbility`（首实例主窗口，`UIABILITY_CREATED` 单例约束）和 `Float`（子窗口）两个变体。多 UIAbility 实例是**第三种机制**：经 `startAbility` 创建的新 EntryAbility 实例主窗口，windowId > 0，但窗口性质是 UIAbility 主窗口。

此路径与现有 `UIABILITY_CREATED` 单例约束冲突（第二个 UIAbility 窗口会被 tao 拒绝），且要求 windowId 语义与 UIAbility 判定解耦（见 4.4）。是否引入这条路径、如何扩展 `OHOSWindowKind` 枚举、如何改造 `wid === 0` 特判，需结合实际场景评估，不在本分析范围内。

### 4.7 结论

| 问题 | 结论 |
|------|------|
| OHOS 平台是否支持多 UIAbility 实例？ | 支持。`startAbility({abilityName:'EntryAbility'})` + `launchType:"standard"` 即可，无需新增第二个 Ability 声明 |
| startNewAbility 做法复杂吗？ | 不复杂。一个 `startAbility` 调用，复用现有 EntryAbility 类 |
| 当前 Tauri 模板能直接用吗？ | 不能。模板未设 launchType（默认 singleton），startAbility 会走 onNewWant 不新建窗口。需把 EntryAbility 的 launchType 改为 standard |
| 多 UIAbility 实例能解决主窗口 resize/move 吗？ | 不能。每个实例主窗口同样系统管理，返回 1300002 |
| 对 windowId 语义的影响 | windowId=0 仅表示第一个默认主窗口，不再表示「是否 UIAbility」；是否 UIAbility 改由枚举参数表示 |
| 多 UIAbility 实例适合什么场景？ | 需要独立生命周期、独立最近任务卡片、独立设备形态/方向的多界面应用 |
